# 0002. 默认使用 SQLite，保留 MySQL 切换能力

- 状态：已采纳（待组长与模块负责人确认）
- 决策时间：2026 年 9—10 月，据《技术选型文档》《数据库设计》等既有文档追溯整理，非会议纪要
- 整理录入：刘克，2026-11-12
- 决策人：待补充（由组长与模块负责人确认后填写）

## 背景

课程仓库会被组外同学克隆试用，评审老师也会在自己机器上跑一次。若强制依赖 MySQL，试用者需要先装数据库服务、建库、配账号，任何一步出错都会导致「跑不起来」。同时答辩现场需要展示规范的表结构设计与 SQL 能力。

## 决策

连接串通过环境变量 `DATABASE_URL` 注入，默认值指向本地 SQLite 文件 `sqlite:///./nanchang_trip.sqlite3`；ORM 使用 SQLAlchemy 2.0，主键类型通过 `BigInteger().with_variant(Integer, "sqlite")` 兼容两种数据库。仓库只提交 `.env.example`，不提交 `.env` 与数据库文件。

## 理由

1. 克隆后执行 `python scripts/init_data.py` 即可得到可演示数据，零外部依赖。
2. 表结构与字段类型按 MySQL 规范设计，切换到 MySQL 只需改一行连接串。
3. 避免把数据库口令提交入库，符合课程对「密钥不入库」的要求。

## 备选方案

| 方案 | 优点 | 缺点 | 为何未采用 |
| --- | --- | --- | --- |
| 只支持 MySQL | 贴近生产环境 | 试用门槛高，容易启动失败 | 与「可一键启动」的评分要求冲突 |
| 只支持 SQLite | 最简单 | 无法体现数据库迁移与类型设计能力 | 答辩时缺少可展示的 MySQL 能力 |
| 引入 Docker Compose | 环境一致 | 需要试用者装 Docker | 留作后续可选，不作为默认路径 |

## 后果

- 两种数据库的差异（自增主键、`ondelete` 级联生效条件）需要在设计文档中说明。
- SQLite 不强制外键约束，业务侧必须自行校验点位有效性——已在路线接口中实现。
- 后期若并发写入增加，应重新评估并迁移到 MySQL。
